\section{Le principe en une image}
% ============================================================

Ton travail passe par quatre endroits. Chaque commande Git fait passer les fichiers de l'un à l'autre.

\begin{center}
\begin{tikzpicture}[font=\footnotesize,
  zone/.style={draw=accentBlue, thin, rounded corners=3pt, fill=accentBlue!8,
    text width=2.3cm, align=center, inner sep=5pt, minimum height=1.5cm},
  arr/.style={-{Stealth[length=5pt]}, accentBlue, thick},
  arrback/.style={-{Stealth[length=5pt]}, successGreen, thick},
  lbl/.style={font=\scriptsize\ttfamily\bfseries, text=accentBlue},
  lblback/.style={font=\scriptsize\ttfamily\bfseries, text=successGreen}]

\node[zone] (work) {\textbf{Dossier de travail}\\[2pt] tes fichiers dans VS Code};
\node[zone, right=1.5cm of work] (index) {\textbf{Index}\\[2pt] ce qui ira dans le prochain commit};
\node[zone, right=1.5cm of index] (local) {\textbf{Dépôt local}\\[2pt] l'historique, dans \texttt{.git}};
\node[zone, right=1.5cm of local] (remote) {\textbf{GitHub}\\[2pt] le dépôt distant};

\draw[arr] (work) -- node[lbl, above] {git add} (index);
\draw[arr] (index) -- node[lbl, above] {git commit} (local);
\draw[arr] (local) -- node[lbl, above] {git push} (remote);

\draw[arrback] (remote.south) .. controls +(0,-1.1) and +(0,-1.1) .. node[lblback, below] {git pull} (work.south);
\end{tikzpicture}
\end{center}

\begin{tcolorbox}[attention, title={Trois erreurs de débutant que ce schéma évite}]
\begin{itemize}
  \item Un \texttt{git commit} \textbf{n'envoie rien} sur GitHub. Tant qu'il n'y a pas eu de \texttt{git push}, ton travail n'existe que sur ta machine.
  \item Un \texttt{git add} \textbf{ne sauvegarde rien}. Il prépare seulement le contenu du prochain commit.
  \item Un fichier modifié après un \texttt{git add} doit être \textbf{ré-ajouté} avant le commit, sinon c'est l'ancienne version qui part.
\end{itemize}
\end{tcolorbox}

% ============================================================
\section{Une seule fois, au tout début}
% ============================================================

Ces étapes ont été faites en semaine 1. Elles ne sont à refaire que sur une \textbf{nouvelle machine}, ou pour un \textbf{nouveau projet}.

\subsection{Une fois par machine --- ton identité}

\begin{lstlisting}[language=bash]
git config --global user.name "Prenom Nom"
git config --global user.email "ton.email@exemple.com"
\end{lstlisting}

\subsection{Une fois par projet --- créer le dépôt}

Le \texttt{.gitignore} se crée \textbf{avant} le premier \texttt{git add} : un fichier entré dans l'historique y reste, même ajouté au \texttt{.gitignore} ensuite.

\begin{lstlisting}[language=bash]
cd ~/Documents/Passerelle/Web/miniforum
git init
git branch -M main
git add .
git commit -m "Structure de base du MiniForum"
git remote add origin https://github.com/ton-login/miniforum.git
git push -u origin main
\end{lstlisting}

\begin{tcolorbox}[astuce, title={Le \texttt{-u} du premier push}]
Il ne sert qu'une fois : il associe ta branche locale \texttt{main} à celle de GitHub. Ensuite, un simple \texttt{git push} suffit pour le reste de l'année.
\end{tcolorbox}

% ============================================================
\section{Le rythme d'une séance}
% ============================================================

\subsection{En arrivant --- récupérer}

Première commande de chaque séance, avant d'écrire la moindre ligne :

\begin{lstlisting}[language=bash]
git pull
\end{lstlisting}

Elle rapatrie ce qui a été poussé depuis une autre machine (celle de la maison, par exemple). Si tu travailles toujours sur le même poste, elle ne fera rien --- ce n'est pas une raison pour l'oublier, c'est justement l'oubli qui crée les conflits.

\subsection{À chaque changement --- le cycle de base}

C'est le cœur de cette fiche. Dès qu'une chose \textbf{fonctionne} ou qu'une étape est \textbf{terminée}, tu commites. Pas plus tard, pas « quand tout sera fini ».

\begin{lstlisting}[language=bash]
git status              # qu'ai-je change depuis le dernier commit ?
git add index.html      # je choisis ce qui entre dans ce commit
git commit -m "Formulaire de creation de sujet"
\end{lstlisting}

Puis on recommence : on code, on teste, on commite. Trois à six commits par séance de TP est un rythme normal.

\begin{tcolorbox}[definition, title={Qu'est-ce qu'un « changement » qui mérite un commit ?}]
Un ensemble cohérent, qui laisse le projet dans un état qui \textbf{fonctionne} et qui se résume en une phrase. Par exemple :
\begin{itemize}
  \item « le \texttt{<header>} et la navigation sont en place » $\rightarrow$ un commit
  \item « la liste des sujets s'affiche depuis le tableau JavaScript » $\rightarrow$ un commit
  \item « j'ai corrigé la faute de frappe dans le titre » $\rightarrow$ un commit
\end{itemize}
À l'inverse, « le TP de la semaine 4 » n'est pas un changement : c'est une séance entière, donc plusieurs commits.
\end{tcolorbox}

\subsection{\texttt{git add} : nommer ses fichiers ou tout prendre ?}

\begin{center}
\renewcommand{\arraystretch}{1.1}
\begin{tabularx}{\linewidth}{p{4.4cm}X}
  \toprule
  \rowcolor{uniNavy}
  \hdr{Commande} & \hdr{Quand l'utiliser} \\
  \midrule
  \rowcolor{uniPaper}
  \texttt{git add index.html} & Le cas normal. Tu sais exactement ce que tu commites. \\
  \texttt{git add index.html style.css} & Plusieurs fichiers d'un même changement. \\
  \rowcolor{uniPaper}
  \texttt{git add .} & Tout ce qui a changé. Pratique, mais seulement \textbf{après} avoir lu \texttt{git status}. \\
  \bottomrule
\end{tabularx}
\end{center}

\subsection{En partant --- envoyer}

\begin{lstlisting}[language=bash]
git push
\end{lstlisting}

Puis rafraîchis la page de ton dépôt sur \texttt{github.com}. Si tes fichiers y sont et que l'onglet \textit{Commits} montre bien ceux de la séance, ton travail est en sécurité.

\begin{tcolorbox}[attention, title={Ne quitte jamais la salle sans avoir poussé}]
Un commit non poussé n'existe que sur le disque de la machine que tu es en train d'éteindre. Le \texttt{git push} de fin de séance est ce qui te permet de reprendre chez toi --- et ce qui rend ton travail visible.
\end{tcolorbox}

\section{Écrire un message de commit}
% ============================================================

Un bon message dit \textbf{ce que fait} le commit, pas ce que tu as touché. Il se lit comme une entrée de journal, à l'infinitif ou au participe, court, sans point final.

\begin{center}
\renewcommand{\arraystretch}{1.1}
\begin{tabularx}{\linewidth}{XX}
  \toprule
  \rowcolor{uniNavy}
  \hdr{À écrire} & \hdr{À éviter} \\
  \midrule
  \rowcolor{uniPaper}
  \texttt{Charpente sémantique de la page d'accueil} & \texttt{modifs} \\
  \texttt{Ajout du formulaire de réponse} & \texttt{index.html} \\
  \rowcolor{uniPaper}
  \texttt{Correction du lien vers sujet.html} & \texttt{ça marche} \\
  \texttt{Passage de la liste de sujets en Flexbox} & \texttt{TP semaine 4} \\
  \bottomrule
\end{tabularx}
\end{center}

\begin{tcolorbox}[astuce, title={Test rapide}]
Relis ton message dans six semaines. S'il ne te dit pas ce que contenait le commit, il est trop vague. « \texttt{modifs} » ne passe jamais ce test.
\end{tcolorbox}

\section{Savoir où j'en suis}
% ============================================================

Trois commandes qui ne modifient rien et qu'on peut lancer sans risque, aussi souvent qu'on veut.

\begin{center}
\renewcommand{\arraystretch}{1.1}
\begin{tabularx}{\linewidth}{p{4.4cm}X}
  \toprule
  \rowcolor{uniNavy}
  \hdr{Commande} & \hdr{Ce qu'elle montre} \\
  \midrule
  \rowcolor{uniPaper}
  \texttt{git status} & Les fichiers modifiés, ceux qui sont prêts à être commités, et si tu es en avance ou en retard sur GitHub. \\
  \texttt{git log -{}-oneline} & L'historique, un commit par ligne. Quitter avec la touche \texttt{q}. \\
  \rowcolor{uniPaper}
  \texttt{git diff} & Ligne par ligne, ce que tu as changé depuis le dernier commit. Quitter avec \texttt{q}. \\
  \bottomrule
\end{tabularx}
\end{center}

\begin{tcolorbox}[definition, title={\texttt{git status} se lit, il ne se subit pas}]
La sortie de \texttt{git status} contient presque toujours la commande à taper ensuite : Git suggère lui-même \texttt{git add}, \texttt{git restore} ou \texttt{git push} selon la situation. Prends le réflexe de la lire en entier avant de chercher ailleurs.
\end{tcolorbox}

\section{Dépannage}
% ============================================================

\subsection{« J'ai oublié de committer pendant deux heures »}

Ce n'est pas rattrapable : le passé n'a pas été enregistré. Commite maintenant, en séparant si possible en deux ou trois commits (\texttt{git add} fichier par fichier), et reprends le rythme. Un historique fait d'un commit géant par séance est signalé à l'évaluation.

\subsection{Mon \texttt{push} est refusé (\textit{rejected})}

Le dépôt distant contient des commits que tu n'as pas en local --- typiquement, tu as poussé depuis une autre machine. La réponse est presque toujours la même :

\begin{lstlisting}[language=bash]
git pull
git push
\end{lstlisting}

\subsection{Git annonce un conflit}

Cela arrive quand la même ligne a été modifiée des deux côtés. Git place les deux versions dans le fichier, entourées de marqueurs :

\begin{lstlisting}
<<<<<<< HEAD
  <h1>Bienvenue sur MiniForum</h1>
=======
  <h1>MiniForum</h1>
>>>>>>> origin/main
\end{lstlisting}

\begin{enumerate}
  \item Ouvrir le fichier concerné dans VS Code (il est signalé en couleur dans l'explorateur).
  \item Garder la version que tu veux, supprimer l'autre \textbf{et les trois lignes de marqueurs}.
  \item Enregistrer, puis :
\end{enumerate}

\begin{lstlisting}[language=bash]
git add le-fichier-concerne.html
git commit -m "Resolution du conflit sur le titre"
git push
\end{lstlisting}

\begin{tcolorbox}[astuce, title={VS Code fait le travail à ta place}]
Au-dessus de chaque conflit, VS Code affiche les boutons \textit{Accept Current Change} / \textit{Accept Incoming Change} / \textit{Accept Both Changes}. Un clic supprime les marqueurs proprement. Vérifie quand même le résultat avant de committer.
\end{tcolorbox}

\subsection{J'ai modifié un fichier et je veux revenir en arrière}

\begin{center}
\renewcommand{\arraystretch}{1.1}
\begin{tabularx}{\linewidth}{p{6.1cm}X}
  \toprule
  \rowcolor{uniNavy}
  \hdr{Situation} & \hdr{Commande} \\
  \midrule
  \rowcolor{uniPaper}
  Annuler mes modifications non commitées & \texttt{git restore fichier.html} \\
  Retirer un fichier de l'index (avant commit) & \texttt{git restore -{}-staged fichier.html} \\
  \rowcolor{uniPaper}
  Corriger le message du dernier commit (non poussé) & \texttt{git commit -{}-amend -m "Nouveau message"} \\
  \bottomrule
\end{tabularx}
\end{center}

\begin{tcolorbox}[interdit, title={\texttt{git restore} détruit du travail}]
Cette commande écrase tes modifications par la dernière version commitée, sans confirmation et sans corbeille. Ne l'utilise que si tu es certain·e de vouloir jeter ce que tu viens d'écrire.
\end{tcolorbox}

\subsection{J'ai committé un fichier qui n'aurait pas dû l'être}

Cas classique : \texttt{node\_modules/} ajouté avant que le \texttt{.gitignore} soit en place. On le sort du suivi tout en le gardant sur le disque :

\begin{lstlisting}[language=bash]
git rm -r --cached node_modules
git commit -m "Retrait de node_modules du suivi Git"
git push
\end{lstlisting}

Vérifie ensuite que \texttt{node\_modules/} figure bien dans le \texttt{.gitignore}, sinon il reviendra au prochain \texttt{git add .}

\subsection{Je travaille sur deux machines (école et maison)}

La règle tient en une ligne : \textbf{\texttt{git pull} en arrivant, \texttt{git push} en partant}, des deux côtés. Si tu oublies le push d'un côté, tu retrouveras l'autre machine en retard et tu risques un conflit.

\begin{tcolorbox}[attention, title={Google Drive n'est pas Git}]
Le dossier \texttt{Passerelle} est synchronisé sur Drive : c'est une sauvegarde contre la panne de disque. Ce n'est \textbf{pas} le canal de transfert entre deux machines. Pour passer d'un poste à l'autre, on passe par GitHub. Laisser Drive et Git écrire en même temps sur le même dossier depuis deux ordinateurs est le meilleur moyen d'abîmer l'historique.
\end{tcolorbox}

\subsection{Je suis perdu·e et je veux repartir propre}

Un dépôt de référence est publié à la fin des semaines 7, 11 et 17. Pour repartir de celui-ci sans perdre ton travail actuel :

\begin{lstlisting}[language=bash]
cd ~/Documents/Passerelle/Web
git clone https://github.com/.../miniforum-reference.git miniforum-s7
\end{lstlisting}

Ton ancien dossier reste intact à côté. Aucune pénalité n'est appliquée : c'est prévu par le cours.

\begin{tcolorbox}[interdit, title={Ne supprime jamais le dossier \texttt{.git}}]
Il est caché à la racine de \texttt{miniforum} et contient \textbf{tout} l'historique du projet. Le supprimer efface l'intégralité de tes commits, définitivement. Aucun problème rencontré dans ce cours ne se règle en effaçant \texttt{.git} --- viens me voir à la place.
\end{tcolorbox}

\section{Mémo}
% ============================================================

\begin{center}
\renewcommand{\arraystretch}{1.15}
\begin{tabularx}{\linewidth}{p{5.2cm}X}
  \toprule
  \rowcolor{uniNavy}
  \hdr{Commande} & \hdr{Effet} \\
  \midrule
  \rowcolor{uniPaper}
  \texttt{git pull} & Récupérer ce qui est sur GitHub. En arrivant. \\
  \texttt{git status} & Faire le point. Aussi souvent que nécessaire. \\
  \rowcolor{uniPaper}
  \texttt{git add fichier} & Préparer un fichier pour le prochain commit. \\
  \texttt{git commit -m "..."} & Enregistrer un point d'étape en local. \\
  \rowcolor{uniPaper}
  \texttt{git push} & Envoyer les commits sur GitHub. En partant. \\
  \texttt{git log -{}-oneline} & Relire l'historique. \\
  \rowcolor{uniPaper}
  \texttt{git diff} & Voir ce qui a changé depuis le dernier commit. \\
  \texttt{git restore fichier} & Jeter les modifications non commitées. \\
  \bottomrule
\end{tabularx}
\end{center}

\vspace{4pt}
\begin{tcolorbox}[definition, title={Réflexe de fin de séance}]
\begin{itemize}
  \item[$\square$] \texttt{git status} ne signale plus de fichier modifié oublié
  \item[$\square$] La séance a produit \textbf{plusieurs} commits, aux messages lisibles
  \item[$\square$] \texttt{git push} a été fait
  \item[$\square$] Le dépôt sur \texttt{github.com} affiche bien les commits du jour
\end{itemize}
\end{tcolorbox}

\vspace{6pt}
\begin{tcolorbox}[attention, title={L'historique compte dans la note}]
La qualité du code et de l'historique Git représente 10\% de la note du projet final, et l'historique est examiné à chaque jalon. Un projet qui apparaît en un seul commit massif donne lieu à un entretien. Committer régulièrement n'est donc pas une coquetterie d'enseignante : c'est la trace de ton travail.
\end{tcolorbox}
